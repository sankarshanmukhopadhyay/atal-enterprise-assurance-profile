# Artifact Model

This document explains how the EAP machine-readable artifacts relate to each other and how they flow through the operational assurance workflow.

## Artifact map

```
catalogs/atal-eap-control-catalog.json          ← canonical control definitions
          │
          ├── catalogs/assurance-level-overlays/EAP-L1-overlay.json
          ├── catalogs/assurance-level-overlays/EAP-L2-overlay.json
          └── catalogs/assurance-level-overlays/EAP-L3-overlay.json
                    │
                    ▼
          artifacts/<level>-checklist.{json,csv,md}     ← generated by generate_profile_checklist.py
                    │
                    ▼ (assessor populates)
          evidence/<bundle>.json                         ← validated by validate_evidence_bundle.py
                    │
                    ▼ (assessor populates)
          assessments/<result>.json                      ← validated by validate_assessment_result.py
                    │
                    ▼
          artifacts/<level>-assessment-report.md        ← compiled by compile_assessment_report.py
```

---

## Catalog

**File:** `catalogs/atal-eap-control-catalog.json` (and `.yaml`)

The catalog is the authoritative source for all control definitions. It defines:

- control IDs, titles, and family membership
- normative statements and rationale
- evidence requirements per control
- ATAL traceability references
- automation candidacy

Controls are never duplicated per assurance level. The catalog defines controls once; overlays determine how they apply.

---

## Overlays

**Files:** `catalogs/assurance-level-overlays/EAP-L{1,2,3}-overlay.json`

Overlays answer the question: *which controls apply at this level, and how?*

Each overlay entry per control specifies:

- `applicable` — whether the control applies at this level
- `normative_strength_override` — whether the strength changes from the catalog default (e.g. SHOULD at L1 becomes MUST at L2)
- `evidence_tightening` — additional evidence requirements beyond the catalog baseline
- `dependency_rules` — controls that must also be assessed if this one applies

Overlays are generated once per release and are version-pinned to the catalog version.

---

## Evidence bundle

**Files:** `evidence/samples/` and instances created by assessors

The evidence bundle is the primary assurance artifact. It contains:

- metadata about the assessed system, assessment period, and attestation
- one `control_evidence_item` per control being assessed
- artifact references (paths or URLs) with optional SHA-256 hashes
- exception references for any waivers

A valid evidence bundle must pass `validate_evidence_bundle.py` before it can be used as input to the report compiler.

**Independent verification:** Evidence bundles are designed to be verifiable without proprietary vendor tooling. The verification steps in `docs/artifact-model.md` (this file) explain how:

1. Obtain the evidence bundle and all referenced artifacts.
2. Recompute the SHA-256 hash of each referenced artifact and compare to the bundle's recorded hash.
3. Confirm attestation metadata is present and plausible.
4. Validate the bundle JSON against `schemas/evidence-bundle.schema.json`.

---

## Assessment result

**Files:** `assessments/samples/` and instances created by assessors

The assessment result records the formal evaluation outcome. It references the evidence bundle and the target overlay, and records:

- a `pass/fail/partial/not_applicable/waived` result per control
- findings with severity and remediation target dates
- residual risks with acceptance records
- a decision block: `conformant`, `non_conformant`, or `conditionally_conformant`

The decision block drives the compiled Markdown report.

---

## Waivers

**Files:** `evidence/templates/waiver.template.json` and instances created by assessors

Waivers are first-class artifacts. They document:

- which control cannot be met and why
- compensating measures in place
- residual risk accepted
- approver identity and approval date
- expiry and review date

Waivers must be approved before the assessment result is finalized. They carry an expiry date to prevent indefinite deferral.

## Generated outputs

Scripts write to `artifacts/` by default:

| File | Produced by |
|---|---|
| `<level>-checklist.{json,csv,md}` | `generate_profile_checklist.py` |
| `<level>-assessment-report.md` | `compile_assessment_report.py` |
| `traceability-matrix.{json,csv,md}` | `build_traceability_matrix.py` |
| `eap-control-catalog-export.{csv,xlsx}` | `export_csv_xlsx.py` |
